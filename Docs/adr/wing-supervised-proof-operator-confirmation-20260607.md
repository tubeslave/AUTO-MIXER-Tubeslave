# ADR: WING Supervised Proof Operator Confirmation - 2026-06-07

## Context

The supervised WING proof runner is the narrow physical write path for the MVP.
It is allowed to exercise only fader and gain-down changes through
`apply_operator_proposal`, followed by rollback and emergency-stop proof. It
must not become a general live-write authority.

## Options considered

1. Keep operator approval as runbook prose only.
2. Add machine-checkable CLI confirmation flags for physical `--execute`.
3. Add an interactive terminal prompt.

## Decision

Use machine-checkable CLI confirmation flags:

- `--operator-confirm-channel`
- `--operator-confirm-value-type`
- `--operator-confirm-delta-db`

The runner requires them when `--execute` is present and blocks before opening
WebSocket if any value is missing or stale.

## Why this won

The proof flow is artifact-driven. CLI confirmation can be generated by the
proof plan, copied into the runbook, stored in `summary.json`, and validated by
the no-WING release gate. It is less ambiguous than prose and easier to test
than an interactive prompt.

## Rejected alternatives

Runbook-only approval was too weak for a physical live-write proof. Interactive
prompting would make automated artifact validation and repeatable dry-run
checks harder.

## Implementation plan

1. Add confirmation args to the physical proof runner.
2. Require matching confirmation only for `--execute`.
3. Emit confirmation facts into the proof summary.
4. Generate the flags from `build_supervised_wing_proof_plan`.
5. Teach `no_wing_release_check` to reject proof-plan commands whose
   confirmation flags are missing or stale.

## Test plan

- `python3 -m py_compile` for changed Python files.
- Focused tests for the proof runner, proof plan, and no-WING gate.
- Quick no-WING release check.
- Full pytest before landing.

## Risks and rollback

The change intentionally breaks older `--execute` commands without confirmation
flags. Rollback is to remove the validation and proof-plan flags, but that would
reopen the stale-command risk.
