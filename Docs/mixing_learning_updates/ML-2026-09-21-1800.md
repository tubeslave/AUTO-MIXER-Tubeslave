## Outcome

The canonical long BSRNN replication paper was read in full and reconciled with repository revision `41e9ce4e796159c7a6e6287d4d198ec1cedbf0ce`. The strongest model result is a compound intervention: larger capacity, longer early-stopping patience, alternative data generation without the paper's SAD path, attention and a PReLU TAC stereo module are combined. It therefore cannot establish that attention, stereo modelling, SAD removal or any other single factor caused the gain.

The implementation audit found three production blockers. First, a missing checkpoint silently creates a randomly initialised model. Second, the public single-file separator peak-normalises the input but does not restore that scale to saved estimates; a silent input can also divide by zero. Third, the fast cSDR path is not contract-equivalent to `museval`: its plain framed SNR, cropping and cross-target silence handling can change which frames and targets contribute.

The current Zenodo v3 record supplies MD5 checksums for three checkpoint archives but shows no licence. Those files can be integrity-checked, but remain `rights_verification_required` and were not downloaded.

## Sources actually read

### SRC-ML-20260921-1500-01 — BSRNN replication family, upgraded

- Canonical full text: [The Costs of Reproducibility in Music Separation Research: a Replication of Band-Split RNN](https://arxiv.org/html/2603.09187), arXiv `2603.09187`, DOI `10.48550/arXiv.2603.09187`, submitted 2026-03-10.
- Related short version: [Investigating the performance and energy costs of replicating Band-Split RNN for Music Source Separation](https://arxiv.org/html/2609.21918), arXiv `2609.21918`, submitted 2026-09-18.
- Reading depth: both versions `full_text_complete`; the longer version is the canonical methodological record. They remain one version family, not independent confirmation.
- Data and task: MUSDB18-HQ, 86/14/50 train/validation/test songs, 44.1 kHz. Training uses three-second chunks and a time-domain L1 plus complex-STFT real/imaginary L1 objective.
- Base and optimized results: the reproduced base reaches test average `7.42` uSDR / `7.65` cSDR, below the original paper's `7.94` / `8.24`; oBSRNN reaches `8.57` / `9.07`, and oBSRNN-SIMO `9.15` / `9.79` in this evaluation.
- Compound treatment: oBSRNN combines the large `N=128, R=12` model, patience 30, alternative augmentation/no SAD, 2-head attention with encoding dimension 16, and PReLU TAC stereo processing. oBSRNN-SIMO additionally changes the source-output topology. No reported factorial design isolates all components.
- Stereo is conditional: naive stereo and TAC with TanH can worsen results; PReLU TAC is the successful reported choice inside the optimized bundle. This does not support a universal “stereo-aware is better” rule.
- Stitching: the authors compare a 10-second/10%-overlap linear fader with three-second rectangular overlap-add. OLA hop changes move some source scores by up to about `0.3 dB` and the 0.5-second hop costs about six times more inference. “Perfect reconstruction” describes the overlap weights for an unchanged signal, not separator additivity, phase safety or perceptual transparency.
- Uncertainty: only the base condition receives a three-seed check; most variants are single runs. Longer patience reduces observed variability but cannot replace a declared multi-seed estimate. Selecting or “tuning” a seed would be an oracle practice, not generalisation evidence.
- SAD result is implementation-specific: alternative data generation performs better here, but the original paper did not isolate the authors' SAD reproduction. This does not show that source-activity detection is generally harmful.
- Energy: the long paper reports about `4,808 kWh` for tabulated models and about `23 MWh` for the whole project, including interrupted, failed and complementary runs. The short-version `24.2 MWh` figure is version-specific drift, not the cost of one clean training run. CodeCarbon values are extrapolated from a few epochs and compared across different GPUs, so they are estimates with different hardware context.
- Limits: no controlled listening, downstream bounded-edit study, sum-consistency test, true-peak/loudness gate, phase/mono test, onset analysis or boundary audibility test.

### AUD-ML-20260921-1500-01 — pinned BSRNN implementation, upgraded

- Repository: [magronp/bsrnn](https://github.com/magronp/bsrnn), revision `41e9ce4e796159c7a6e6287d4d198ec1cedbf0ce`; code licence MIT; execution `false`.
- Checkpoint loading: `instanciate_src_model` calls `load_from_checkpoint(..., strict=False)` only if the expected path exists; otherwise it prints an initialization message and creates a fresh random model. The evaluation and separation paths do not fail closed.
- Gain contract: `separate.py` divides the input by its absolute maximum, restores the input tensor afterward, but saves model estimates without multiplying them by that maximum. Saved stems therefore lose the input gain scale. A zero or non-finite maximum is not guarded, so silence can produce division-by-zero/NaN output.
- Metric contract: fast cSDR is framed unscaled SNR, while the official path calls `museval.metrics.bss_eval`. Fast cSDR crops to its computed frame span and marks every target for a frame as `NaN` if any reference or estimate target is exactly silent. One silent target can therefore erase valid evidence for the other targets.
- Reproducibility: configuration has seed 42 but deterministic execution is disabled. The only metric comparison under `helpers/eval.py::__main__` prints results from random tensors; it is not a regression assertion.
- Stitching: rectangular OLA multiplies every chunk by `hop/segment`, which is a constant-overlap assumption; the fader uses alternating linear fade-out/fade-in chunks. Neither path asserts finite output, exact coverage, boundary continuity, mixture additivity, peak safety or phase/mono preservation.
- Optimized config parity: the public `bsrnn-opt` YAML encodes attention and PReLU TAC, but patience 30 is supplied separately by training commands. Reproducing the paper requires the command/config/checkpoint tuple, not the model YAML alone.
- Energy code: Board Management Controller energy is hard-coded to zero; CodeCarbon totals are linearly extrapolated from logged epochs and multiplied by PUE. These are estimation conventions, not direct measurements of complete runs.
