### Paper-to-code correspondence

The implementation formula `-20*log10(1 + 19d)` matches the paper's direct-level mapping and reaches approximately −26 dB at `d=1`. The nearby source comment incorrectly says the endpoint is −14.3 dB; the executable formula, paper equation and paper table agree with one another. The code also matches the published high-shelf mapping (0 to −14 dB, 8 kHz to 2.5 kHz), wet mapping (0 to 45%), pre-delay (0 to 30 ms), 300 Hz low-mid peak (0 to +2.5 dB), parallel Freeverb topology and constant-power dry/wet crossfade.

The implementation additionally maps `d` to Freeverb room size, damping and a sigmoid HRTF blend. Those derived controls are part of the actual treatment bundle even though the headline table lists only gain, shelf, wet and pre-delay. A future test must freeze or preregister them explicitly rather than calling the treatment merely “reverb amount”.

### Reproducibility and implementation limits

1. **Promised evaluation artifacts are absent.** The paper points to the repository for further data and analysis, but the audited revision contains source/UI files and embedded IR assets only; no participant-level data, analysis notebook/script, spectral-validation test, saved benchmark result, unit tests or GitHub Actions workflow was found.
2. **Clean build is not reproducible as published.** `CMakeLists.txt` uses an author-local absolute JUCE path (`E:\\University\\Medialogy\\JUCE`). The JUCE 8.0.8 `FetchContent` path is commented out. Building therefore requires a manual project edit and was not attempted.
3. **The benchmark is performance-only.** `DistanceBenchmark` times `processBlock()` on block sizes 64–512 at 48 kHz, `d={0,1}` and HRTF on/off. It has no correctness assertions and no committed output. The same buffer is processed repeatedly after being filled once, so it is not a controlled signal-quality or spectral-validation test.
4. **Default HRTF loading depends on the GUI path.** The processor constructor does not load the embedded KEMAR IR. It is loaded in the editor constructor (or explicitly by the benchmark). A restored/headless instance whose editor never opens can have `hrtf_on=true` while the convolution stage remains unloaded, making that control ineffective.
5. **The HRTF crossfade ramp is block-size dependent.** Its smoother is configured in samples for 50 ms, but `getNextValue()` is called once per audio block. At 48 kHz the effective transition is approximately 3.2 s at 64 samples and 25.6 s at 512 samples, not 50 ms. This does not invalidate steady-state mapping, but it blocks claims about consistent HRTF automation.
6. **Asset rights need separate confirmation.** The source code is Apache-2.0, while the embedded KEMAR IRs are third-party measurement assets. No asset-specific licence or notice was found in the repository; the root licence alone is not treated as confirmation that the IRs may be redistributed or integrated.
7. **Absolute custom-IR state is not portable.** The saved plugin state records the local file path. Moving a session between machines can leave the custom IR unavailable, with no embedded copy in the project state.

### Revised bounded conclusion

The coupled-cue concept remains a plausible production hypothesis, and the source implements the advertised steady-state mappings closely enough to define a controlled manual A/B. Confidence cannot increase from the paper's `N=18` result because the promised evaluation data are not public in the audited revision, the comparator construction remains underspecified, and several build/headless/automation paths are untested. Exact values remain study/implementation facts, not production presets.

## Knowledge Cards added/revised

1. **A published mapping can match code while the evaluation remains unreproducible.** Formula correspondence supports implementation fidelity, not the listening-test effect size.
2. **A deterministic macro must enumerate all derived controls.** In this implementation, distance also changes room size, damping and HRTF blend; leaving them implicit violates a one-factor preregistration.
3. **GUI-dependent initialization is unsafe for automated/headless audio.** A parameter state is not proof that the DSP resource it controls has been loaded.
4. **Smoother duration must be checked at the call site.** A sample-count smoother advanced once per block creates block-size-dependent timing.
5. **A timing benchmark is not a signal-quality test.** CPU measurements without assertions, fixed reference output or committed results cannot validate spectral error, artifact freedom or audio equivalence.
6. **Repository licence and bundled-asset rights are separate questions.** External IR redistribution needs explicit provenance and terms.
7. **An incorrect comment is not an implementation result.** Here, the gain comment is wrong while the formula and paper agree; the formula is the authoritative implementation fact.
