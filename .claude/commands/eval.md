# /eval — eval-driven development

`/eval [define|check|report] [имя]`

Принцип: определи проверяемые критерии успеха ДО написания кода. Для этого проекта
два типа эвалов (подробности и шаблоны — `.claude/evals/README.md`):

## Тип 1: DSP-эвалы (синтетические сигналы)

Для изменений в DSP (LUFS, true peak, EQ biquads, gate, компрессия, phase alignment):

- **Capability**: тест на синтетическом сигнале с известным ожидаемым результатом
  (синус известной амплитуды → известный LUFS; известная задержка → gcc_phat её находит
  с правильным знаком; ступенька уровня → gate с заявленным hysteresis)
- **Regression**: существующие тесты `tests/` проходят без изменений порогов
- Эталоны: ITU-R BS.1770-4, Audio EQ Cookbook — см. «DSP стандарты» CLAUDE.md

## Тип 2: Mixing-rule эвалы (проба на железе)

Для правил микширования (eq.tonal_targets, gain staging, автобаланс) — пайплайн:
кандидат → проба на WING → вердикт оператора → счёт.

- **Grader — оператор**, не модель: слуховой вердикт на реальном звуке обязателен
- Метрика pass@k по нескольким пробам; правило принимается в canon только после
  подтверждённых вердиктов
- Проба обязана соблюдать safety: bounded moves, fader ≤ 0 dBFS, true peak < -1.0 dBTP

## Подкоманды

### /eval define <имя>
Создай `.claude/evals/<имя>.md` по шаблону из README, заполни критерии вместе с оператором
ДО реализации.

### /eval check <имя>
Прогони capability-эвалы (pytest для DSP; для mixing-rules — подготовь пробу и жди вердикта
оператора), допиши результаты в `.claude/evals/<имя>.log` с датой.

### /eval report <имя>
Сведи историю прогонов: pass@1/pass@3 по capability, pass^k по regression,
статус: READY / NEEDS WORK / BLOCKED.

## Правила

1. Эвалы определяются до кода — это заставляет продумать критерии
2. Код-грейдеры (pytest) где возможно; оператор-грейдер для всего, что звучит
3. Regression-эвалы для safety-путей (fader ceiling, feedback, snap safety) — pass^k = 100%,
   без исключений
4. Эвалы версионируются вместе с кодом
